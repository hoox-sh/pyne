# VS Code Extension

## Abstract

**PYNE** (`hoox-sh.pyne` **0.5.3**) is a **LanguageClient host** plus a rich TextMate grammar, branded as part of the **HOOX open trading stack**. It does **not** reimplement language intelligence in TypeScript — `vscode-languageclient` speaks STDIO to `pyne-lsp` (then alias `pynescript-lsp`, then `python -m pynescript.langserver`) and forwards whatever that process advertises in `initialize`. The VSIX stays **0.5.3**; the hosted Python server is **`hoox-pyne` 0.6.28** (`src/pynescript/__about__.py`). The extension maps **`.pyne` (first-class)** plus `*.pine` / `*.pinev5` / `*.pinev6` / `*.pinescript` to language id `pinescript`, ships **snippets**, and exposes a broad `pynescript.*` settings surface with per-feature toggles.

## Conceptual model

```mermaid
flowchart LR
  VS[VS Code] --> EXT[extension.ts activate]
  EXT --> LC[LanguageClient]
  LC -->|stdio| LSP[pyne-lsp 0.6.28]
  EXT --> TM[TextMate grammar]
  TM --> HL[Token colors]
  LSP --> CAP[advertised ServerCapabilities]
  CAP --> UI[range tokens / on-type / linked edit / inlay / links / color]
```

### Hosted `pyne-lsp` methods (not reimplemented in TypeScript)

The LanguageClient negotiates capabilities from `src/pynescript/langserver/config.py` (`get_server_capabilities`). The hosted server now advertises the following; the 0.5.3 extension is still only a host, but adds client-side **feature gates** so each capability can be toggled without restarting the server.

| LSP method | What the editor gets | Feature page |
| --- | --- | --- |
| `textDocument/semanticTokens/full` + `/range` | Same legend, range clipped to the viewport | [Semantic tokens](/pyne/docs/lsp/features/semantic-tokens) |
| `textDocument/onTypeFormatting` | Format the just-completed line; trigger `"\n"` | [Formatting](/pyne/docs/lsp/features/formatting) |
| `textDocument/linkedEditingRange` | Same-document live ranges for a user ident (keywords / builtin namespaces refused) | [Linked editing](/pyne/docs/lsp/features/linked-editing) |
| `textDocument/inlayHint` + `inlayHint/resolve` | Assignment type labels; parameter-name hints on dotted builtin calls (`ta.sma(close, 14)` → `source:` / `length:`). Resolve fills type `textEdits` only | [Inlay hints](/pyne/docs/lsp/features/inlay-hints) |
| `textDocument/documentLink` + `documentLink/resolve` | `http://` / `https://` URLs in comments (`//`, `/* */`, hash `# …`) and string literals. Resolve fills `tooltip` with the URL when tooltip is unset | [Document links](/pyne/docs/lsp/features/document-link) |
| `textDocument/documentColor` + `colorPresentation` | `#hex` (and named `color.*` / literal `color.rgb` / `color.new` / `color()` / `color.from_gradient`) swatches; presentation rewrites as `#rrggbb` / `#rrggbbaa` | [Document color](/pyne/docs/lsp/features/document-color) |

Also advertised (unchanged host path): diagnostics, completion + resolve, hover, signature help, definition / references, highlight + rename, document / workspace symbols, full + range formatting, folding, selection range, Convert-to-v6 / W001 / W002 / C002 code actions. Capability table: [Architecture](/pyne/docs/lsp/architecture).

`[pinescript]` configuration defaults already set `editor.semanticHighlighting.enabled` to `true` and `editor.defaultFormatter` to `hoox-sh.pyne`. Format-on-type and linked-editing UX are standard VS Code editor settings (`editor.formatOnType`, `editor.linkedEditing`) — they are **not** `pynescript.*` keys. Enable them if you want Enter to hit `onTypeFormatting` or rename-as-you-type to hit `linkedEditingRange`.

Feature gates are enforced **client-side** by middleware that reads the setting live, so toggling a `pynescript.*.enabled` key takes effect immediately — no server restart. Diagnostics, completion snippets, and formatting are passed as initialization options too.

Initialization options object:

```json
{
  "formattingEnabled": true,
  "snippetsEnabled": true,
  "diagnosticsEnabled": true
}
```

Docker stdio example (`lsp.command` = `docker`):

```json
{
  "pynescript.lsp.command": "docker",
  "pynescript.lsp.args": [
    "run", "--rm", "-i",
    "-v", "${workspaceFolder}:/work", "-w", "/work",
    "ghcr.io/hoox-sh/pyne/lsp:0.6.28"
  ]
}
```

That image is the Python language server (**0.6.28**), not the VSIX.

## Internals

| Path | Role |
| --- | --- |
| `vscode-extension/src/extension.ts` | Activate / deactivate / client / middleware gates |
| `vscode-extension/package.json` | Contributes + scripts |
| `vscode-extension/syntaxes/pinescript.tmLanguage.json` | Grammar |
| `vscode-extension/snippets/pine.code-snippets` | Snippets |
| `vscode-extension/language-configuration.json` | Brackets / comments |
| `vscode-extension/src/test/` | `@vscode/test-electron` tests |
| `out/extension.js` | Compiled JS |

Server launch (`resolveLspLaunch` in `extension.ts`):

1. If `pynescript.lsp.command` is not `auto`, spawn that command with `lsp.args`.
2. Else try `pyne-lsp`, then `pynescript-lsp`, on `PATH`.
3. Else try `pynescript.lsp.python`, then `pynescript.install.python`, then `python3` / `python` / `py` with `-m pynescript.langserver`.
4. Else status-bar error and the install offer (below).

No `--parent-dir` / `PYTHONPATH` rewrite. Transport is STDIO. Release packaging expects `pyne-lsp` on `PATH` (pip, Nuitka onefile, or `docker run --rm -i ghcr.io/hoox-sh/pyne/lsp:0.6.28`). The **VSIX stays 0.5.3**; the GHCR tag tracks the Python package (`__about__.py` **0.6.28**), not the extension version.

### Automatic install

When `resolveLspLaunch` finds nothing and `lsp.command` is `auto`, the extension can install the server itself:

- `install.autoInstall = true` → install immediately (no prompt).
- `install.autoPrompt = true` (default) → one-time modal prompt: **Install now** / **Later** / **Don't ask again** (sets `autoPrompt=false`).
- **PYNE: Install Language Server** → run it manually at any time.

The flow resolves an interpreter (`install.python` → `lsp.python` → `python3` → `python` → `py`), requires Python ≥ 3.10 and pip, then runs:

```bash
<python> -m pip install --upgrade --disable-pip-version-check <install.args…> "hoox-pyne[lsp]"
```

pip output streams to the **PYNE Language Server** output channel under a cancellable progress notification. On success the client restarts; on failure the last lines are logged.

When the resolved Python is **externally managed** (PEP 668 — common on Debian/Ubuntu), `install.createVenv` (default `true`) makes the extension create an isolated virtualenv under its global storage (`install.venv` overrides the path), install there, and record the venv interpreter in `install.python` so module launch uses it. Set `install.createVenv = false` to install into the system Python instead. Installs are deduplicated, so the prompt and palette command cannot run concurrently.

### Backend and Pro (`Run on Pro`)

The extension talks to a PYNE backend for `Run on Pro`. Two modes:

**Local / self-hosted** — point at `backend.url` (default `http://127.0.0.1:5002`):

```json
{
  "pynescript.pro.enabled": true,
  "pynescript.backend.url": "http://127.0.0.1:5002"
}
```

**Hosted PYNE Pro** — flip the hosted toggle; the effective URL becomes `backend.hostedUrl` (default `https://pynescript.online`) and an API key is required:

```json
{
  "pynescript.pro.enabled": true,
  "pynescript.pro.apiKey": "pyn_…",
  "pynescript.backend.useHosted": true
}
```

`pro.apiKey` is password-masked. **PYNE: Run on Pro** sends `{ script, data, symbol, mode }` to `{backend}/run`; the `Authorization: Bearer <key>` header is added only when a key is set (hosted always requires it). `backend.url`/`backend.hostedUrl` are base URLs only (no trailing `/run`).

**Install / start / test:**

- **PYNE: Install Backend (Pro API)** installs `backend.package` (default `hoox-pyne[pro,lsp]`) with the same pip/venv flow as the language server.
- **PYNE: Start Backend** runs `python -m backend.app` from `backend.path` (or the workspace folder) in a terminal, with `PORT` taken from the backend URL. Requires a PYNE checkout containing `backend/app.py`.
- **PYNE: Test Backend Connection** GETs `{backend}/health`.

### Themes (Void / Volt / Orange)

Two independent options:

| Option | Setting | Values | `none` means |
| --- | --- | --- | --- |
| **Workbench theme** | `pynescript.theme` | `none` · `void` · `volt` · `orange` | Keep the user/system theme |
| **Syntax highlighting** | `pynescript.syntaxHighlighting` | `none` · `void` · `volt` · `orange` | Use the active theme's Pine colors |

The workbench theme sets the UI chrome and hover cards (`editorHoverWidget.*`, `editorSuggestWidget.*`). The syntax option sets only the Pine TextMate + semantic token colors (keywords and functions → accent, strings → accent tint, numbers → foreground, comments/punctuation/series builtins → neutral gray), so you can keep your own editor theme and still get AXIS Pine highlighting.

| Theme | Accent | Notes |
| --- | --- | --- |
| **PYNE Void** | indigo `#939FFF` | Near-black surfaces |
| **PYNE Volt** | lime `#B7EF09` | Neutral surfaces with a whisper of lime |
| **PYNE Orange** | signal orange `#FE6A00` | Warm signal accent |

Switch with **PYNE: Select Workbench Theme** / **PYNE: Select Syntax Highlighting**, or set the keys directly. Defaults: workbench `none`, syntax `void`.

## Invariants and edge cases

1. **`lsp.enabled === false` skips starting the client** — output channel, status bar, and palette commands still register so the palette never shows “command not found”; restart then no-ops until the setting is true.
2. **Binary vs module:** production users should install `hoox-pyne[lsp]` or the Nuitka onefile (`pynescript-lsp-*` on GitHub Releases) and set `pynescript.lsp.command` if not on PATH.
3. **Grammar works without LSP** — open a `.pyne` or `.pine` file offline and still get TextMate highlighting.
4. **`.pyne` is first-class** in `package.json` extensions + activation; legacy `.pine*` / `.pinescript` remain fully supported.
5. File watcher covers every associated suffix (`pyne`, `pine`, `pinev5`, `pinev6`, `pinescript`).
6. **VSIX 0.5.3 does not pin server methods.** Range tokens, on-type format, linked editing, inlay resolve / param names, document links + resolve tooltip, and document color appear only when the spawned `pyne-lsp` is new enough to advertise them (this tree: **0.6.28**). Feature gates are client-side and read live settings.

## Worked example — extension development

```bash
pip install -e ".[lsp]"
cd vscode-extension && npm ci && npm run compile
# Launch Extension Development Host pointing at vscode-extension
```

Open a fixture `.pine` file; confirm Problems panel shows parse/lint diagnostics from the Python server. With a current `pyne-lsp`, also expect `#hex` color swatches, clickable `https://` links in comments, `source:` / `length:` inlay labels on `ta.sma(close, 14)`, and range semantic tokens while scrolling.

## Failure modes

| Symptom | Cause |
| --- | --- |
| “Language client failed to start” | `pyne-lsp` missing / wrong command |
| No squiggles, highlighting OK | LSP disabled or server crash; check Output → PYNE Language Server |
| Restart does nothing | Client never started (`lsp.enabled` false) |
| No inlay param names / color swatches / document links | Spawned `pyne-lsp` is older than this tree (need **0.6.28**) |
| Enter does not reformat the previous line | `editor.formatOnType` is off (not a `pynescript.*` key) |
| Identifiers do not multi-cursor as you type | `editor.linkedEditing` is off (not a `pynescript.*` key) |
| A feature does nothing after toggling | Its `pynescript.<feature>.enabled` key is `false` |
| **Run on Pro** says “disabled” | Set `pynescript.pro.enabled` (and `pro.apiKey` for hosted) |
| **Run on Pro** request fails | Check `pynescript.backend.url` / `backend.useHosted` (base URL, no `/run`) and that the backend is reachable |
